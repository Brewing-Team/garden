4. GPU Zen Frequently Asked Questions
	Last modification: August 21st, 2023
	Why should you write an article for this book?  
	Articles in books offer the advantage of a thorough and thoughtful coverage of a certain topic, vested and created with great care by a group of experts.  
	The whole process of writing an article should be enjoyable and instructive for the inquisitive mind.  
	This book series aims to provide technical help to graphics programmers. There are no “paid by a corporation” articles and the main motivation is not in the hiring needs, licensing, selling, or marketing needs of a company. It covers a topic with much more detail compared to a PowerPoint slide deck and because we require source code aims to make the resulting technique reproducible.  
	Compared to any other form of publishing your knowledge, these books are stored in the Library of Congress. This guarantees a longer life span, compared to conference talks and websites.
	Which is the target group of the book?  
	The intermediate to advanced programmer.
	What are the minimum requirements of a Proposal?  
	A proposal needs to show that you actually implemented the technique. So screenshots are most important (with the exception of a pure article on math) and a short description of the algorithm. Please indicate if you provide an example application with full source code. If you can prove that the technique you are going to describe shipped in a game, this is a big plus.
	Is an accepted proposal a guarantee that my article will be published?  
	The article will be dropped if the author
	1. does not hit a sufficient quality level: this is for example the case if the technique just does not work
	2. and does not hit the deadlines
	3. provides an article that is not understandable. This might be for example the case if the English in the article was generated by an online translation service.
	How many pages are expected for each contribution?  
	Different topics need a different level of depth to explain them. So the expectation is that the topic is explained sufficiently. Sometimes this can happen on one page and sometimes it will take up to 30 book pages.
	What writing standards is the contribution expected to conform to?  
	A lot of readers won't be native English speakers. So it is important to write an easy to translate English. You have two challenges: you have to explain your technique for the intermediate and advanced programmers target group and you have to explain it in a way that the non-English-speaking part of this group of people is able to understand it easily. Pictures are sometimes worth more than a thousand words. So use them as often as possible. Movies should get priority 3 in your "production" process after text and example production. Code snippets are another way to sharpen an explanation very efficiently. Don't do "academic obfuscation": your readers will likely appreciate a code snippet with a nested loop instead of a smart-looking equation with a triple integral.
	I always try to make certain, that my papers cover the following areas:  
	1) What is the topic of this paper or this section of this paper?  
	2) Why is the topic important? Where is the topic used or applicable?  
	3) Presentation of any theory behind the topic, derivations, etc.  
	4) Algorithmic statement of the approach/solution  
	5) Presentation of the approach/solution  
	6) Analysis (strengths, weaknesses, etc.)  
	7) Concluding remarks  
	8) References
	(1) and (2) are important for setting the context. (4) makes understanding (5) much easier.
	It is expected that the author runs something equivalent to a language checker over the article before the section editor is supposed to read it.
	What is the required file format?  
	To create a collaborative environment, this book project will use Overleaf.com. To achieve a unified layout, example article implementations named Smith.tex, Smith.bib are provided. The expectation is that authors follow those.  
	There are also style files and layout files. Those should not be changed because they define the layout of the final book.
	What image formats are supported?  
	To make the process less error-prone, it is expected that everyone provides their images as uncompressed PNGs with lossless quality.
	What is an acceptable image resolution?  
	In general bigger is better. We encourage the authors to think about the resolution rather in terms of printing resolution, dots/inch (dpi). Our target recommended resolution is 300 dpi. This means that a 1080p image would be 1920/300=6.4 inches wide on the actual printed paper. If you need to make your image smaller, this is fine too, because it would lead to higher than 300 dpi. However, all images should have at least 300 dpi pixel density for printing.
	What are the rules for citation?  
	Please consult the tex template in Overleaf.com to follow the right citation rules. There is a Smith.bib file and then there is a reference in Smith.tex.
	What programming environment and conventions is the example application expected to conform to?  
	An example application is preferable for every article. Our readers represent different types of “learners”. Some people learn programming by checking other people’s sources; others read a lot of pages, before diving into a piece of source.  
	The expected CPU programming language is C or C++. Any GPU programming language is acceptable. To make code easier to understand, C code is preferable over C++. Many game engines are written by balancing a C core with some high-level C++ features.  
	To illustrate your article with an example application with less effort, rendering frameworks like bgFX ([https://github.com/bkaradzic/bgfx](https://github.com/bkaradzic/bgfx) ), The Forge ([https://github.com/ConfettiFX/The-Forge](https://github.com/ConfettiFX/The-Forge) ), and others are recommended.  
	All the example code will be published on GitHub in a GPU Zen 3 repository.
	Can I post my article and my example application on my website?  
	Yes.
	What is a typical workflow for an article?  
	Following the typical schedule of a GPU Zen book, we have the following phases:
	1. Proposal phase: after the call for authors, potential authors are expected to send in a proposal that outlines their article and example application. An example proposal is provided.
	2. Writing begins: writing happens in Overleaf.com as described above, following the style and layout guidelines distilled in the files.  
		Following the proposal the section editor will work with the author on setting the right targets so that the article can be finished in the most efficient way.
	3. First draft: The first results should be “feature-complete” and from the perspective of the author in a publishable state.
	4. Edits: the section editor will go through the article on Overleaf.com and provide guidance on how to present the technique covered. He provides help on how to cover the advantages and disadvantages better and how to structure the article.
	5. Final draft: the final draft will be moved into its appropriate section in the “GPU Zen” book project on Overleaf.com. The author and section editor will make sure it aligns with the layout guidelines of the book.
	6. All editors then will read the articles at least two times before the book goes to print and any editor might come back to the author with questions.
	7. The book will be printed in color on demand on Amazon.com. It will be printed directly in the countries where Amazon offers a printing-on-demand service. The main drawback of this approach is that the print quality might not be consistent between different countries.  
		Nevertheless, because printing books locally has less ecological impact, printing on demand is a favorable and conscious way of making books.
	Please note that the only guaranteed feedback phases are in No. 3, 4, and 6.
	Will I get paid to write an article?
	With the previous book series, we had arrangements where authors got a certain percentage of the profits depending on the number of pages they wrote. Not much profit was made.
	Later on, we had a flat fee for a while. With the production cost of the books so high and the naturally small number (~3000?) of books sold, the publishers decided to drop the whole book series to pursue higher profit margin projects. This happened throughout the book industry with many computer graphics books, as you might have noticed.
	For the GPU Zen books, we decided that selling them with a loss is not such a big problem as long as we do it in “our own” publishing house named Black Cat Publishing. This is why we offered the electronic copies for $1.98 (GPU Zen) or $2.99 (GPU Zen 2).  
	Additionally, the GPU Zen books are printed on demand. There is no discount for printing a larger number of books. In other words, the profit per book sold is always the same.  
	One other economic factor is the ability of Amazon to change the price to their liking. We underestimated that fact for the first book and determined the price based on what profits we needed. Amazon immediately cut the price in half, so some of the books sold at a loss right away until they raised it a bit higher. For the second book, we just doubled the asking price expecting Amazon to lower it. This is why the second book is more expensive than the first book.
	That all being said. So far GPU Zen 1 and 2 were produced at a loss. We are planning to produce GPU Zen 3 again with a loss. This time the loss might be covered by a corporate sponsor.
	With all this said, will I get anything apart from honor, fame, and my name in golden letters?
	We are planning to give every author and editor a hard copy of the book. Because Amazon doesn’t give us many “free Author copies” we are going to pay for it.  
	We also plan to have a T-Shirt for Authors and a T-Shirt for Editors. We are asking the corporate sponsor to pay for this and his logo might be on the T-Shirt.
5. There’s a substantial body of literature on rendering shadows in real time, both for hard and soft shadows generated by different types of lights. Most of the work on soft shadows, however, use a combination of filtering and assumptions to simplify the calculations such as ignoring the shape of the light source. Of particular interest, percentage-closer soft shadows [\[Fernando 05\]](http://developer.download.nvidia.com/shaderlibrary/docs/shadow_PCSS.pdf) proposes a variable filtering size that is also proportional to the light blocker’s distance. As a potential improvement, one could also use a texture based kernel for the PCF step to approximate different light shapes, but it would be prohibitively expensive for big penumbra sizes.
	  
	This chapter focuses on an approximation, inspired by depth of field splatting techniques, that identifies points of high variance in a shadow map and reuses such points to project a slice of the light source shape. By doing this, not only the cost of searching, filtering and sampling the depth map is lowered, but it also lets the user define an artistic definition of the light shape, making certain effects like rendering crescent shadows possible. It can also be used to render non-photoreal effects.
	  
	Because it is designed for environments with high-frequency shadow maps, it is ideal for scenes with many trees or any geometry that can generate small pinholes. The proposed technique is subtractive and can be implemented on top of any other conventional shadow mapping algorithm while considering mitigations to potential spatiotemporal artifacts.
	  
	Try out the demo and check out the Unity source code [on GitHub!](https://github.com/wolfgangfengel/GPUZen2/tree/master/03_Shadows/01_Soft%20Shadow%20Approximation%20for%20Dappled%20Light%20Sources/Demo)

6. Computing light visibility for a directional light in a scene spanning many kilometers can be a challenging task. But why is it important? A modern open-world game usually features fully dynamic lighting environments reacting to time of day, weather conditions, in-game events etc. Since physically-based rendering became widely adopted in game engines, not having an accurate visibility term available can easily break the image under certain lighting conditions thus making the point of having PBR moot.  
	A game would often rely on a stack of methods for shadows generation simply because there's no single algorithm that meets its performance and quality requirements. Take the cascaded shadow maps algorithm as an example of popular well-rounded approach to shadows rendering. The algorithm might not scale well for large scenes with the number of objects rendered into the cascades quickly becoming a bottleneck. Thus, one may choose to use cascades only for a small subsection of the scene close to the player, while shadows for the remaining parts of the scene will be created with some less accurate yet faster algorithm.
	Perhaps the simplest method to accelerate shadow map rendering is lowering frequency of shadow map updates. Normally, a shadow map is rendered every frame. Now suppose we render a shadow map once per several frames, so that each frame in this group uses the same cached shadow map for lighting, thus distributing costs of single update over multiple frames. This way shadow map rendering effectively becomes cheaper as the number of frames reusing this cached data grows.

	Some state-of-the-art methods therefore use the GPU to implement approximate ray tracing techniques to achieve acceptable performance levels. These methods are hard to implement though.
	  
	Screen space/image space light ray tracing methods have limitations like SSR techniques. They can’t reliably follow light rays through a complex scene. Of course, multi-layer images or voxel-based structures can help to work around this, but they come at a steep memory cost and high implementation complexity.
	  
	DirectX™ Raytracing (DXR) removes all these limitations and provides a standard API for fast GPU accelerated ray tracing and acceleration structure-based GPU-side scene management.
	  
	With DXR you can trace a sufficiently high number of rays to implement real-time raytraced caustics without any of the shortcomings of image based or voxel-based methods.
	  
	The GPU Zen 2 chapter ‘ Real-Time Ray-Traced One-Bounce Caustics’ describes a technique that uses DXR based raytracing to implement realistic one bounce surface caustics. The algorithm described can run in parallel to work on the 3D queue using asynchronous compute. If your game has enough other graphics workloads you may be able to run raytraced caustics almost for ‘free’.

9. Tileable textures are a commonly used tool to add detail to 3D scenes. However, when texturing large areas or designing highly detailed surfaces using tileable textures and detail maps, tiling patterns quickly become visible. Typically, reducing repetition patterns requires using larger textures or hiding the visible repetition with additional objects.  
	  
	[Heitz and Neyret](https://eheitzresearch.wordpress.com/722-2/) recently introduced a new by-example procedural texturing method that solves this issue for textures with stochastic appearances. This technique is usable in real-time applications thanks to order-of-magnitude faster performance than previous state-of-the-art methods. It relies on a simple tiling-and-blending scheme of the texture space, combined with a new histogram-preserving blending operator.  
	  
	In this chapter we look into a detailed implementation of the method, that we release as an [OpenGL project](https://github.com/wolfgangfengel/GPUZen2/tree/master/04_3D%20Engine/02_Procedural%20Stochastic%20Textures%20by%20Tiling%20and%20Blending). The new blending operator requires dedicated precomputations, while the tiling-and-blending algorithm requires a fast run-time shader implementation. We detail  improvements made to the original article along the way in the interest of usability in video-game production, reducing processing times and adapting to texture filtering and compression. We offer an implementation of the prototype for Unity as well: [Procedural Stochastic Texturing in Unity](https://blogs.unity3d.com/2019/02/14/procedural-stochastic-texturing-in-unity/).
